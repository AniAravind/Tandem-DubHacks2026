# Private planning, shared trip, individual payments

1. The organizer plans a trip in a direct iMessage conversation. `group_state.mode=private_planning` tells the agent to collect dates, destination, intended group size, and rough search budget. Searches can use the future trip size without inventing members in the private conversation.
2. After the organizer chooses a searched option or requests a proposed rough-plan link, `publish_plan(option_id, title, summary)` copies the searched options and public trip facts into a separate web group. It preserves the selected place, authoritative price, dates, and expected headcount. It never copies chat messages or named private budgets. Repeated publication of the same option returns the same plan.
3. The server attaches a signed organizer URL privately, outside the model's tool results. The organizer enters their registered name/number there, then copies the public `/p/<plan-id>` group invite. The public invite never contains the organizer token.
4. Friends enter name and E.164 phone number and explicitly accept the trip plan. There is no signup, password, SMS verification, or passkey enrollment. A signed HttpOnly browser cookie identifies their membership. Numbers are stored as hashes plus last four digits, never shown to other participants. This is deliberately unverified demo identity. A phone number alone cannot reclaim another browser's existing membership.
5. Each acceptance records a ballot for the selected plan. The organizer's place is reserved; joining stops at the intended headcount. Once everyone has joined and accepted, the organizer opens collection. The existing vote/rules transition creates exactly one purchase for the entire roster. Joining and publishing never authorize a hold.
6. Each signed-in participant sees their own exact share and personal consent link. Existing card tokenization, explicit consent, hold, capture, decline, leave, deadline, and fallback flows handle payments. A link returns from consent to the trip plan. All payment/authentication assertions remain simulated. The join roster is frozen once collection starts.

Public previews expose only the shared plan, selected listing facts, and participant count. Member names and personal payment links require the joined browser session. Published groups reject demo member-header impersonation. Public links are capability-style unguessable UUIDs and expire for joining after seven days. Organizer capability links also expire after seven days.

Only the private source conversation's outbox is delivered to Photon; frontend group updates stay in the shared website group. No iMessage group support is needed. Existing web demo groups retain their original behavior.

Validation: real rules-engine tests cover future-roster search, idempotent publication, privacy, owner capability, duplicate join, capacity/owner reservation, origin checks, complete-roster funding, unique consent links, payment approvals through booking, and header impersonation rejection. Run `python manage.py test purchases.tests.test_plans`, the complete backend suite, frontend build, and lint.

Private model context uses the user’s requirements plus authoritative searched options and publications. Earlier assistant replies are excluded so obsolete membership errors cannot become current planning facts. A claimed organizer link without a successful publish_plan triggers correction; unresolved claims are replaced by an honest incomplete-state message. Link text and sharing instructions are generated by the server. Requesting a rough-plan link can publish the top-ranked actual match as a proposal; joining still explicitly accepts it and payment approval remains separate.

Explicit short requests such as Add or Send me the organizer link publish or resend from saved real options without an AI round trip. When a longer invite request performs a fresh search, the server completes publication if the model stops at listing choices. A top-ranked proposed option is used only when no explicit choice exists; resending preserves the previously chosen plan. Publishing still creates no hold or booking.

## General buying and solo plans

The private Photon assistant now saves an explicit buying brief per conversation (goal, category, buyer count, confirmed budget, requirements, qualitative recommendations). A changed brief invalidates older search options for publication. One buyer is supported; “me and four friends” means five buyers.

`save_buying_brief` stores intent, not payment authorization. `publish_buying_plan` creates an unpriced page for categories without supported offers. Such plans have nullable `selected_option`/`vote`, `checkout_ready: false`, nullable price fields, and cannot open payment collection. Existing quoted-plan routes and consent contracts remain unchanged. Private organizer links are attached by the server, outside model tool results. Public pages contain only the explicitly published brief.

Run `python manage.py seed_buying_catalog` once after deployment to add clearly simulated gift offers. This command preserves existing groups, users, offers, and purchases. All checkout and authentication remain simulated. Generic planning does not imply live inventory or purchasing support from arbitrary merchants.

Verification: backend coverage includes persisted-price reply filtering, goal changes, stale-option rejection, arbitrary-category planning with payment rejection, single-buyer gift capture, and four-buyer gift capture. Real Groq verification exercised gift → priced plan/private link, then telescope → separate solo planning page/private link.

## Choice handling and message presentation

Private number/ordinal/exact-title replies select a current saved option and publish its private organizer link without an AI request. Numeric Photon input is handled during ingestion, so provider limits and Celery delays cannot make it repeat the shortlist. Duplicate provider receipts remain deduplicated, and repeated selections reuse the plan. Invalid or superseded choices ask for a valid current selection; they never silently choose a different offer.

Fresh search results stay associated with the current buying brief even when the model saves the brief after searching. Only matching results executed in that same turn are adopted; older persisted options remain superseded. Updating summary/recommendation copy alone preserves the revision. Older queued private turns are dropped when a newer user input has arrived, so they cannot bury a newly published link.

New private search presentations use a short server-generated title and numbered cards with authoritative prices. `shared/message-text.mjs` cleans legacy Markdown for iMessage and web chat, preserves signed URLs, and converts pipe tables into readable numbered entries. Web chat adds visual title/paragraph hierarchy; iMessage uses plain title lines because text messages do not interpret Markdown. The assistant uses a warm, lightly playful voice with restrained emojis and labels catalog offers as simulated.

The frontend uses the supplied navy emblem without embedded lettering in headers, chat avatars, and favicon. The transparent mark was prepared with the built-in imagegen tool from the supplied reference (prompt: isolate the navy emblem; preserve geometry; remove lettering and paper background).
