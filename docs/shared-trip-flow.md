# Private planning, shared trip, individual payments

1. The organizer plans a trip in a direct iMessage conversation. `group_state.mode=private_planning` tells the agent to collect dates, destination, intended group size, and rough search budget. Searches can use the future trip size without inventing members in the private conversation.
2. After the organizer chooses a searched option and is ready to share, `publish_plan(option_id, title, summary)` copies the searched options and public trip facts into a separate web group. It preserves the selected place, authoritative price, dates, and expected headcount. It never copies chat messages or named private budgets. Repeated publication of the same option returns the same plan.
3. The server attaches a signed organizer URL privately, outside the model's tool results. The organizer enters their registered name/number there, then copies the public `/p/<plan-id>` group invite. The public invite never contains the organizer token.
4. Friends enter name and E.164 phone number and explicitly accept the trip plan. There is no signup, password, SMS verification, or passkey enrollment. A signed HttpOnly browser cookie identifies their membership. Numbers are stored as hashes plus last four digits, never shown to other participants. This is deliberately unverified demo identity. A phone number alone cannot reclaim another browser's existing membership.
5. Each acceptance records a ballot for the selected plan. The organizer's place is reserved; joining stops at the intended headcount. Once everyone has joined and accepted, the organizer opens collection. The existing vote/rules transition creates exactly one purchase for the entire roster. Joining and publishing never authorize a hold.
6. Each signed-in participant sees their own exact share and personal consent link. Existing card tokenization, explicit consent, hold, capture, decline, leave, deadline, and fallback flows handle payments. A link returns from consent to the trip plan. All payment/authentication assertions remain simulated. The join roster is frozen once collection starts.

Public previews expose only the shared plan, selected listing facts, and participant count. Member names and personal payment links require the joined browser session. Published groups reject demo member-header impersonation. Public links are capability-style unguessable UUIDs and expire for joining after seven days. Organizer capability links also expire after seven days.

Only the private source conversation's outbox is delivered to Photon; frontend group updates stay in the shared website group. No iMessage group support is needed. Existing web demo groups retain their original behavior.

Validation: real rules-engine tests cover future-roster search, idempotent publication, privacy, owner capability, duplicate join, capacity/owner reservation, origin checks, complete-roster funding, unique consent links, payment approvals through booking, and header impersonation rejection. Run `python manage.py test purchases.tests.test_plans`, the complete backend suite, frontend build, and lint.
